# Feature Specification: 游戏别名管理

**Feature Branch**: `006-game-alias-management`  
**Created**: 2026-06-01  
**Status**: Draft  
**Input**: User description: 在管理中心中，添加一个游戏别名管理功能。其中包括字段：ID、名称、别名（字符串数组）、 创建日期、修改时间。System和Super管理员拥有全部权限，Normal管理员只读权限。

## Clarifications

### Session 2026-06-01

- Q: 前端别名编辑器交互方式？ → A: Tags 输入组件（Ant Design Select mode="tags"），用户逐个输入别名，每个别名显示为可删除的 Tag 标签，支持回车添加和点击删除
- Q: 别名去重策略？ → A: 前后端双重去重 — 前端在提交前自动去除重复项（UX 友好），后端作为权威再次去重并存储（数据安全）。此外，不同游戏之间的别名也不能相同（全局唯一）
- Q: 别名数据模型设计？ → A: 独立 `game_alias_entries` 表（一对多）— `games` 表存游戏基本信息，`game_alias_entries` 表每行存一个别名，`alias` 字段加唯一索引，天然保证全局唯一
- Q: 搜索范围？ → A: 同时搜索名称和别名 — 用户输入关键词时，同时匹配游戏名称和别名字段，返回所有相关游戏

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看游戏别名列表 (Priority: P1)

管理员登录后可以查看游戏别名列表，列表展示所有已配置的游戏及其别名信息，包括 ID、名称、别名、创建日期和修改时间。系统管理员和超级管理员可以进行编辑和删除操作，普通管理员只能查看。

**Why this priority**: 这是游戏别名管理的基础功能，所有其他操作都建立在列表展示之上。

**Independent Test**: 可以独立测试列表的加载、分页、数据展示准确性。

**Acceptance Scenarios**:

1. **Given** 管理员已成功登录，**When** 管理员导航到游戏别名管理页面，**Then** 系统加载并展示游戏别名列表，包含 ID、名称、别名、创建日期、修改时间
2. **Given** 普通管理员已登录，**When** 管理员查看游戏别名管理页面，**Then** 页面只展示列表数据，不显示添加、编辑、删除按钮
3. **Given** 系统管理员或超级管理员已登录，**When** 管理员查看游戏别名管理页面，**Then** 页面展示列表数据，并显示添加、编辑、删除按钮
4. **Given** 游戏别名列表数据量较大，**When** 页面加载完成，**Then** 列表支持分页展示，每页默认显示 10 条记录

---

### User Story 2 - 添加游戏别名 (Priority: P2)

系统管理员和超级管理员可以添加新的游戏别名记录，填写游戏名称和一个或多个别名，系统保存后更新列表。

**Why this priority**: 这是管理游戏别名的核心操作，允许管理员扩展游戏别名配置。

**Independent Test**: 可以独立测试添加功能，验证数据保存和列表更新。

**Acceptance Scenarios**:

1. **Given** 系统管理员或超级管理员已登录，**When** 管理员点击"添加游戏别名"按钮，填写名称和别名并提交，**Then** 系统创建新的游戏别名记录，列表刷新显示新记录
2. **Given** 系统管理员正在添加游戏别名，**When** 管理员未填写名称就提交，**Then** 系统提示"名称不能为空"
3. **Given** 系统管理员正在添加游戏别名，**When** 管理员填写了已存在的游戏名称并提交，**Then** 系统提示"游戏名称已存在"
4. **Given** 普通管理员已登录，**When** 管理员查看游戏别名管理页面，**Then** 页面上不显示"添加游戏别名"按钮

---

### User Story 3 - 编辑游戏别名 (Priority: P2)

系统管理员和超级管理员可以编辑已有的游戏别名记录，修改游戏名称或别名列表，系统保存后更新修改时间。

**Why this priority**: 允许管理员修正或更新游戏别名配置，是日常维护的常见操作。

**Independent Test**: 可以独立测试编辑功能，验证数据更新和时间戳变更。

**Acceptance Scenarios**:

1. **Given** 系统管理员或超级管理员已登录，**When** 管理员点击某条游戏别名的"编辑"按钮，修改名称或别名并提交，**Then** 系统更新该记录，修改时间更新为当前时间
2. **Given** 系统管理员正在编辑游戏别名，**When** 管理员将名称修改为已存在的其他游戏名称并提交，**Then** 系统提示"游戏名称已存在"
3. **Given** 普通管理员已登录，**When** 管理员查看游戏别名列表，**Then** 列表中每条记录的"编辑"按钮不显示

---

### User Story 4 - 删除游戏别名 (Priority: P3)

系统管理员和超级管理员可以删除不再需要的游戏别名记录，删除前需要确认。

**Why this priority**: 允许管理员清理无效或过期的游戏别名配置。

**Independent Test**: 可以独立测试删除功能，验证数据删除和确认流程。

**Acceptance Scenarios**:

1. **Given** 系统管理员或超级管理员已登录，**When** 管理员点击某条游戏别名的"删除"按钮并确认删除，**Then** 系统删除该记录，列表刷新不再显示该记录
2. **Given** 系统管理员点击"删除"按钮，**When** 管理员在确认对话框中点击"取消"，**Then** 系统不执行删除操作，记录保持不变
3. **Given** 普通管理员已登录，**When** 管理员查看游戏别名列表，**Then** 列表中每条记录的"删除"按钮不显示

---

### Edge Cases

- 游戏名称唯一性：同一游戏名称不能重复添加
- 别名全局唯一 + 去重策略：前后端双重去重（前端提交前 Set 去重，后端 HashSet + DB UNIQUE 索引作为最终权威），确保同一游戏内和跨游戏的别名字符串均全局唯一
- 别名不能为空数组：添加或编辑时至少需要一个别名
- 名称和别名长度限制：名称最多 50 字符，每个别名最多 50 字符
- 别名数量限制：每个游戏最多 20 个别名
- 删除确认：删除操作必须有确认对话框，防止误删
- 权限边界：前端隐藏按钮只是 UX 优化，后端必须对每个操作执行权限检查并返回 403 + 错误码 2001（权限不足）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须以列表形式展示游戏别名，包含 ID、名称、别名、创建日期、修改时间
- **FR-002**: 系统必须支持搜索游戏别名，搜索关键词同时匹配游戏名称和别名字段，返回所有相关游戏
- **FR-003**: 系统必须支持分页展示游戏别名列表，默认每页 10 条
- **FR-004**: 系统必须支持系统管理员和超级管理员添加游戏别名，使用 Tags 输入组件（Ant Design Select mode="tags"）逐个输入别名，每个别名显示为可删除的 Tag 标签
- **FR-005**: 系统必须支持系统管理员和超级管理员编辑游戏别名，修改名称或别名列表
- **FR-006**: 系统必须支持系统管理员和超级管理员删除游戏别名，删除前要求确认
- **FR-007**: 系统必须保证游戏名称唯一，添加或编辑时验证名称不重复
- **FR-008**: 系统必须验证别名数组不为空，且每个别名非空字符串
- **FR-009**: 系统必须在添加或编辑时对别名进行前后端双重去重（前端提交前去重，后端存储前再次去重），且所有别名在整个系统中全局唯一（不同游戏不能有相同别名）
- **FR-010**: 系统必须记录创建日期和修改时间，修改时间随每次编辑自动更新
- **FR-011**: 系统必须根据管理员角色控制权限：System 和 Super 管理员拥有全部权限，Normal 管理员只有只读权限
- **FR-012**: 前端按"无权限 = 不渲染"约定隐藏不可用控件；后端必须对每个受保护 API 执行权限检查并返回 403 + 错误码 2001
- **FR-013**: 系统必须对名称和别名进行长度验证，名称最多 50 字符，每个别名最多 50 字符
- **FR-014**: 系统必须限制每个游戏的别名数量不超过 20 个
- **FR-015**: 所有交互元素必须支持键盘导航与符合 WCAG 2.1 AA 级对比度，并使用语义化 HTML 与 ARIA 标签
- **FR-016**: 后端必须在游戏别名创建/修改/删除事件上写入结构化审计日志（操作者 ID、目标游戏 ID、操作类型、时间）

### Key Entities

- **Game (游戏)**: 游戏基本信息，包含：
  - ID: 唯一标识（BIGINT，自增）
  - 名称: 游戏名称（VARCHAR，唯一）
  - 创建日期: 记录创建时间（DATETIME）
  - 修改时间: 最后修改时间（DATETIME）

- **GameAliasEntry (游戏别名条目)**: 单个别名条目，与游戏一对多关联，包含：
  - ID: 唯一标识（BIGINT，自增）
  - game_id: 所属游戏 ID（外键）
  - alias: 别名字符串（VARCHAR，唯一，全局去重）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可以在 2 秒内加载完成游戏别名列表（首屏 10 条）
- ~~**SC-002**: 95% 的管理员可以无需培训即可完成游戏别名的增删改查操作~~ — 排除出 buildable SC，属于可用性测试指标
- **SC-003**: 不同角色的权限隔离 100% 准确，无越权访问
- **SC-004**: 游戏别名列表页面通过 axe-core 自动检测时 0 个 critical / serious 违规项
- **SC-005**: 系统支持至少 1000 条游戏记录（每条可关联最多 20 个别名）

## Assumptions

- 游戏别名管理作为管理中心的一个子模块，复用现有管理中心的认证和权限体系
- 数据模型采用一对多设计：`games` 表存储游戏基本信息，`game_alias_entries` 表存储每个别名单独一行，`alias` 字段加唯一索引保证全局唯一
- 日期时间格式统一为 YYYY-MM-DD HH:mm:ss，使用服务器 UTC 时间，前端根据浏览器本地时区格式化
- 系统采用前后端分离架构，前端使用 React + TypeScript + Ant Design，后端使用 Rust + axum
- 管理员角色沿用现有定义：1=Normal（只读），2=System（全部权限），3=Super（全部权限）
- 不需要游戏别名版本历史或审计追溯（除基础审计日志外）
