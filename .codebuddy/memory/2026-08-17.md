## ⚠️ 关键发现：kind 字段类型分裂（潜伏生产 bug，2026-08-17 第八轮专项审计）

### 核心结论
`functions.kind` / `tools.kind` 存在**三套矛盾定义**，是潜伏的生产 decode 失败 bug：
- `entity_store::Function.kind: i64` / `Tool.kind: i64`（整数，UI 层真正使用的实体）
- `entity_store::init_tables` 的 `kind INTEGER`（旧 DDL）
- `migrations.rs` v4 的 `kind TEXT DEFAULT 'builtin'`（新 DDL，权威）
- `function_store::FunctionKind` / `tool_store::ToolKind` 枚举（字符串）

### 执行顺序与最终 schema
`Store::new`（store.rs:1009）先 `migrate_to_current`（v4，TEXT）→ 再 `run_migrations`（init_tables，INTEGER 但 `IF NOT EXISTS` 跳过）→ **最终 schema = TEXT**。

### 触发路径（真实 bug）
1. **Function**：v4 迁移后 `kind` 存 `'builtin'/'custom'/'placeholder'`（字符串），`Function::list/get` 的 `try_get::<i64>("kind")` → **decode 失败**，Function 管理 UI/测试执行器崩溃。
2. **Tool（双重失败）**：读 `'function-wrap'` 进 i64 decode 失败；且写整数 `1/2` 触发 v4 tools 表的 `CHECK (kind = 'function-wrap'...)` 约束失败。
3. **WorkflowNode.node_type**：无分裂（`entity_store` 已是 String）。

### 为什么测试全 Green 掩盖了它
- 大多数测试用独立 `*Store::new(pool)`（in-memory 或独立 pool），不经过 `entity_store::Function/Tool`。
- `migration_compatibility.rs` 的 `v2_maps_function_and_tool_kinds_and_legacy_llm_fields_exactly` 验证了迁移后 kind 是字符串 `["custom","placeholder","builtin"]` / `["function-wrap","workflow-wrap"]`，但**从不调用 `Function::get`/`Tool::get` 验证 decode**。
- 生产 `Store::new/open` 必先走 v4 migration → TEXT → entity_store 读 i64 必崩。

### 根因
两套迁移体系并存（`migrations.rs` v4 TEXT vs `entity_store::run_migrations` INTEGER），靠 `IF NOT EXISTS` 侥幸让 TEXT 生效，但 `entity_store` 实体定义从未同步改成字符串。

### 修复方案（建议，未执行）
统一到字符串 kind（对齐 v4 + FunctionKind/ToolKind 枚举）：
1. `entity_store::Function.kind` / `Tool.kind`：`i64` → `String`
2. `Function::create/update` / `Tool::create/update`：签名 + `.bind(kind)` 改字符串
3. `entity_store::init_tables` 的 `kind INTEGER` → `TEXT`（消除双定义）
4. UI 层 `function_view.rs`（`form_kind: i64` + `function_kind_label(kind: i64)` 映射 1/2/3）和 `tool_view.rs`（`form_kind: i64` + `kind_label()` 映射 1/2）适配字符串
5. 补测试：v4 迁移后 `Function::get`/`Tool::get` decode 成功（当前完全缺失）

这是跨 2 实体 + 2 DDL + 2 UI view + 补测试的高风险重构，涉及数据迁移正确性，需用户明确批准后执行。
